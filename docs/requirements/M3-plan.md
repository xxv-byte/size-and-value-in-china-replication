# M3 计划：下一步优化建议（requirements）

日期：2026-10-26　分支：`m3-optimization-plan`　状态：计划中

## 1. 为什么做

前两期里程碑（M1 和 M2）主要建立了项目的过程基线和持续集成（CI）机制，确保了代码在合成数据上的可运行性。然而，根据 `docs/REPRODUCTION_STATUS.md` 中暴露的局限性，本仓库距离精确复现原论文还存在“数据口径”和“代码架构”两方面的瓶颈。

M3 的目标是提供一份明确的优化蓝图，解决遗留的代理变量、样本缺口以及 Jupyter Notebook `%run` 机制带来的性能与可维护性问题，从而将复现状态从“部分复现”向“完全复现”推进。

## 2. 优化建议内容

### 2.1 数据与方法论（Methodology & Data）

解决 `REPRODUCTION_STATUS.md` 第 3 节和第 5 节指出的主要差异：

1. **真实数据全量重跑**：
   - 现状：由于资源限制，完整真实数据重跑未在本轮执行。现有结论基于 2026-10 的历史运行。
   - 建议：在配备充足内存的机器上，使用完整的 RESSET 真实数据重跑 `CH_3_factors.ipynb`，更新 Table 3/4/5 的结论。
2. **合并报表口径对齐（ConFlg）**：
   - 现状：未过滤 `ConFlg`（合并/母公司标志），导致财务指标提取可能混杂母公司数据。
   - 建议：在 `clean_and_universe_2.ipynb` 的清洗逻辑中，增加对 `ConFlg` 字段的筛选逻辑，确保统一使用合并报表（如 `ConFlg == '1'`）。
3. **拆分 A 股股本计算市值**：
   - 现状：市值计算使用 `Fullshr` 未拆分 A 股与 A+B+H 股本。
   - 建议：依据论文口径，在 `features_3.ipynb` 中修正市值计算公式，仅使用 A 股流通/总股本进行权重分配。
4. **提升 EP 和 ROE 代理指标精度**：
   - 现状：EPS 未扣除非经常性损益（扣非）；ROE 直接使用系统日频给定的 TTM 字段。
   - 建议：补全 1998–2006 的财报数据，手动计算基于“扣非净利润/总市值”的 EP，并使用原始财报数据重新构造 ROE，减少代理误差。

### 2.2 架构与性能（Architecture & Performance）

解决 `docs/RUNNING_GUIDE.md` 和 `REPRODUCTION_STATUS.md` 中关于内存和执行效率的痛点：

1. **重构 `%run` 魔法命令链**：
   - 现状：代码通过 Jupyter 的 `%run` 进行流水线式调用，这会导致内存中保留大量的中间 DataFrame（如 18M 行的日表），极易造成 OOM，且上游代码被多次重复执行。
   - 建议：逐步将 `src_jup/` 下的核心数据处理逻辑重构为标准的 Python 模块（如 `src/data_pipeline.py`、`src/features.py`），利用 `import` 调用函数并在函数结束后释放局部变量内存。
2. **中间结果持久化（Checkpointing）**：
   - 现状：每次改动下游都需从头运行上游耗时的 I/O 操作。
   - 建议：在耗时较长的数据清洗（S2）和特征计算（S3）步骤后，引入 `.parquet` 格式的数据快照落盘机制。下游代码直接读取 Parquet 文件，避免重新计算。

## 3. 下一步执行顺序

建议将 M3 拆分为以下子里程碑：
- **M3.1 架构解耦**：优先解决 `%run` 和内存问题，将核心计算逻辑提取为 `.py` 脚本，同时确保 `tests/` 全部通过。
- **M3.2 数据清洗精化**：引入 `ConFlg` 和 A 股股本分母的过滤修正。
- **M3.3 真实数据验收**：进行最终的全量 RESSET 数据跑批验证，输出全新的复现报告。
